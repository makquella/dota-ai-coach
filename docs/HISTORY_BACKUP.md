# Резервна копія історії

Виправлення F03 аудиту підготовлено в **0.53.6**. Формат файлу залишається `wardly-backup`, версія **1**; міграція SQLite, `ANALYSIS_VERSION` і `TRIM_VERSION` не змінюються.

`GET /player/backup` читає гравців, матчі, налаштування, cache й вибраний акаунт в одній read transaction. SQLite WAL зберігає спільний знімок навіть під час запису через інше з'єднання. Launcher пакує JSON у gzip; перенесення за кодом використовує той самий backup API.

`POST /player/backup` спершу перевіряє весь файл, потім відкриває одну `BEGIN IMMEDIATE` transaction. До неї входять злиття чотирьох таблиць і прив'язка акаунта, якщо на комп'ютері ще не вибрано свого. Внутрішній merge helper не робить проміжних commit. Помилка SQL чи commit відкочує всі записи цієї операції. Очищення планів і запуск синхронізації відбуваються після успішного commit. Інші фонові операції можуть і далі змінювати історію своїми транзакціями.

## Валідація й сумісність

- Версія — додатний integer; `true`, нуль, від'ємні й дробові значення відкидаються. Новіша версія дає `newer_version`.
- Наявні відомі таблиці мають бути списками об'єктів. Відсутні таблиці вважаються порожніми; невідомі таблиці й колонки ігноруються.
- Account/match IDs — додатні integer у межах SQLite int64; bool не вважається ID. Числові summary-колонки мають бути int64, прапорці — `0`/`1`/bool, текст — рядком. Необов'язкові колонки допускають `null`.
- OpenDota, timeline та analysis JSON мають бути об'єктами; `items` — списком рядків. Перевіряються основні вкладені контейнери історії/facts, відомі JSON-налаштування й форми coach cache: об'єкт розбору або список об'єктів запитань. JSON `null` у cache зберігає попередній зміст явного cache miss. Це мінімальна перевірка контейнерів, а не повна перевірка контракту всіх версій analysis і всіх фактів.
- JSON відкидає NaN, Infinity, переповнення float і поодинокі Unicode surrogates. Timestamp cache — скінченне невід'ємне число, під час запису перетворюється на float.
- Метадані цього комп'ютера й секрети виключаються в обох напрямках. Імпортується лише `coach:` cache; OpenDota cache запитується наново. Вміст виключених рядків не імпортується й не потребує перевірки.

Злиття зберігає наявні значення, нотатки й вибір акаунта; заповнюються лише порожні поля. Повторне завантаження того самого файлу не створює дублікатів. Пошкоджений відомий рядок відкидає весь файл; попереднє мовчазне пропускання некоректних значень припинено.

Некоректний файл повертає HTTP 400 `not_backup`. Збій SQLite повертає HTTP 503 `restore_failed`: дані цієї операції не збережено. Launcher показує окреме повідомлення українською й англійською. Diagnostics scope `history-backup` містить лише клас помилки, без вмісту файлу й тексту SQLite exception.

## Пошкоджений cache

`cache_get` перетворює пошкоджений JSON, хибний відомий контейнер чи timestamp на cache miss. Запис видаляється умовно за ключем, попереднім значенням і timestamp: оновлення іншим SQLite connection після читання не буде видалене. Diagnostics scope `player-cache` не містить ключа, payload чи traceback. Перевірка пошкодження виконується й для прострочених рядків.

Якщо видалення неможливе, читання все одно повертає miss і окремо позначає помилку очищення; після усунення причини очищення повториться. Запити до провайдера йдуть наявним шляхом і з попередніми налаштуваннями. Розбори й відповіді AI буде перестворено лише за звичайними правилами застосунку, з урахуванням налаштувань і доступності провайдера. Виправлення не ремонтує вже пошкоджених match blobs і не обіцяє відновлення за фізичного псування файлу SQLite.

## Перевірки

`test_backup_atomicity.py` використовує HTTP, реальні SQLite triggers, deferred foreign key для помилки commit, повторне відкриття бази й окремі з'єднання з `Events`. Перевіряються відсутність SQL-запису до завершення валідації, rollback чотирьох таблиць і linking, збереження нотаток, повторний імпорт, відсутність часткових даних в іншого читача й узгодженість експорту за зовнішнього writer.

`test_cache_corruption.py` перевіряє безпечний HTTP-розбір, diagnostics, помилку видалення й гонку із зовнішнім refresh. `test_history_backup.py` зберігає round trip між комп'ютерами й заборону перенесення ключів. Через зміну спільного store потрібен увесь backend suite; перевірка launcher і Windows packaging проходить у CI.

## Автоматичні копії (0.53.55)

`backend/app/auto_backup.py` зберігає копії тієї самої історії (`wardly-backup`, без ключів і налаштувань цього комп'ютера) у `<дані>/backups/`, gzip, атомарний запис через тимчасовий файл. Лаунчер запитує `POST /player/backups/auto` через дві хвилини після старту бекенда й далі раз на добу, але не під час матчу; бекенд вирішує сам: копія `weekly`, якщо найновішій тиждень, або `update`, якщо версія застосунку змінилася від останньої копії (історія, якою її залишила попередня версія). Порожня історія не копіюється. Зберігаються не більше `KEEP` = 4 копій і не більше 200 МБ разом; старі видаляються першими, найновіша залишається завжди. Поруч із копією лежить маленький `.info.json` із кількістю матчів, тому список не розпаковує копій.

Перемикач «Автоматичні копії» в «Налаштування → Історія матчів» (meta `auto_backup` = `off`), «Зробити копію зараз» (`manual`), список копій. «Перевірити» викликає `GET /player/backups/{id}/preview`: той самий merge, що й під час відновлення, виконується в `BEGIN IMMEDIATE` і відкочується (`PlayerStore.preview_backup`), тож попередній перегляд показує точні числа доданих і заповнених рядків і нічого не пише. «Відновити» (`POST …/restore`) — звичайний атомарний імпорт: лише додає відсутнє. Пошкоджена копія дає `not_backup`, невідома — 404, хибне ім'я — 422.

Перед зміною схеми SQLite (`schema_version` у файлі менше за `SCHEMA_VERSION`) `PlayerService` до відкриття сховища робить копію самого файлу через SQLite backup API: `coach-pre-schema-<версія>-<час>.sqlite3`, зберігаються дві останні. Це ручне відновлення на крайній випадок, застосунок їх не читає.

Тести: `test_auto_backup.py` (weekly/update/off/порожня історія, ротація за кількістю й бюджетом, попередній перегляд без запису й відновлення, пошкоджені й невідомі копії, знімок перед зміною схеми, спільні правила перевірки).
