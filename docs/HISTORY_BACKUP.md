# Резервная копия истории

Исправление F03 аудита подготовлено в **0.53.6**. Формат файла остаётся `wardly-backup`, версия **1**; миграция SQLite, `ANALYSIS_VERSION` и `TRIM_VERSION` не меняются.

`GET /player/backup` читает игроков, матчи, настройки, cache и выбранный аккаунт в одной read transaction. SQLite WAL сохраняет общий снимок даже при записи через другое соединение. Launcher упаковывает JSON в gzip; перенос по коду использует тот же backup API.

`POST /player/backup` сначала проверяет весь файл, затем открывает одну `BEGIN IMMEDIATE` transaction. В неё входят слияние четырёх таблиц и привязка аккаунта, если на компьютере ещё не выбран свой. Внутренний merge helper не делает промежуточных commit. Ошибка SQL или commit откатывает все записи этой операции. Очистка планов и запуск синхронизации происходят после успешного commit. Другие фоновые операции могут продолжать менять историю своими транзакциями.

## Валидация и совместимость

- Версия — положительный integer; `true`, ноль, отрицательные и дробные значения отвергаются. Более новая версия даёт `newer_version`.
- Присутствующие известные таблицы должны быть списками объектов. Отсутствующие таблицы считаются пустыми; неизвестные таблицы и колонки игнорируются.
- Account/match IDs — положительные integer в границах SQLite int64; bool не считается ID. Числовые summary-колонки должны быть int64, флаги — `0`/`1`/bool, текст — строкой. Необязательные колонки допускают `null`.
- OpenDota, timeline и analysis JSON должны быть объектами; `items` — списком строк. Проверяются основные вложенные контейнеры истории/facts, известные JSON-настройки и формы coach cache: объект разбора либо список объектов вопросов. JSON `null` в cache сохраняет прежний смысл явного cache miss. Это минимальная проверка контейнеров, а не полная проверка контракта всех версий analysis и всех фактов.
- JSON отвергает NaN, Infinity, переполнение float и одиночные Unicode surrogates. Timestamp cache — конечное неотрицательное число, при записи преобразуется в float.
- Метаданные этого компьютера и секреты исключаются в обоих направлениях. Импортируется только `coach:` cache; OpenDota cache запрашивается заново. Содержимое исключённых строк не импортируется и не требует проверки.

Слияние сохраняет существующие значения, заметки и выбор аккаунта; заполняются только пустые поля. Повторная загрузка того же файла не создаёт дубликатов. Повреждённая известная строка отвергает весь файл; прежнее молчаливое пропускание некорректных значений прекращено.

Некорректный файл возвращает HTTP 400 `not_backup`. Сбой SQLite возвращает HTTP 503 `restore_failed`: данные этой операции не сохранены. Launcher показывает отдельное сообщение на русском и английском. Diagnostics scope `history-backup` содержит только класс ошибки, без содержимого файла и текста SQLite exception.

## Повреждённый cache

`cache_get` превращает повреждённый JSON, неверный известный контейнер или timestamp в cache miss. Запись удаляется условно по ключу, прежнему значению и timestamp: обновление другим SQLite connection после чтения не будет удалено. Diagnostics scope `player-cache` не содержит ключа, payload или traceback. Проверка повреждения выполняется и для просроченных строк.

Если удаление невозможно, чтение всё равно возвращает miss и отдельно отмечает ошибку очистки; после устранения причины очистка повторится. Запросы к провайдеру идут существующим путём и с прежними настройками. Разборы и ответы AI будут пересозданы только по обычным правилам приложения, с учётом настроек и доступности провайдера. Исправление не ремонтирует уже повреждённые match blobs и не обещает восстановление при физической порче файла SQLite.

## Проверки

`test_backup_atomicity.py` использует HTTP, реальные SQLite triggers, deferred foreign key для ошибки commit, повторное открытие базы и отдельные соединения с `Events`. Проверяются отсутствие SQL-записи до завершения валидации, rollback четырёх таблиц и linking, сохранение заметок, повторный импорт, отсутствие частичных данных у другого читателя и согласованность экспорта при внешнем writer.

`test_cache_corruption.py` проверяет безопасный HTTP-разбор, diagnostics, ошибку удаления и гонку с внешним refresh. `test_history_backup.py` сохраняет round trip между компьютерами и запрет переноса ключей. Из-за изменения общего store требуется весь backend suite; проверка launcher и Windows packaging проходит в CI.

## Автоматические копии (0.53.55)

`backend/app/auto_backup.py` хранит копии той же истории (`wardly-backup`, без ключей и настроек этого компьютера) в `<данные>/backups/`, gzip, атомарная запись через временный файл. Лаунчер спрашивает `POST /player/backups/auto` через две минуты после старта бэкенда и затем раз в сутки, но не во время матча; бэкенд решает сам: копия `weekly`, если самой новой неделя, или `update`, если версия приложения сменилась с последней копии (история, какой её оставила прежняя версия). Пустая история не копируется. Хранятся не больше `KEEP` = 4 копий и не больше 200 МБ вместе; старые удаляются первыми, самая новая остаётся всегда. Рядом с копией лежит маленький `.info.json` с числом матчей, поэтому список не распаковывает копии.

Переключатель «Автоматические копии» в «Настройки → История матчей» (meta `auto_backup` = `off`), «Сделать копию сейчас» (`manual`), список копий. «Проверить» вызывает `GET /player/backups/{id}/preview`: тот же merge, что и при восстановлении, выполняется в `BEGIN IMMEDIATE` и откатывается (`PlayerStore.preview_backup`), так что предпросмотр показывает точные числа добавленных и заполненных строк и ничего не пишет. «Восстановить» (`POST …/restore`) — обычный атомарный импорт: только добавляет недостающее. Повреждённая копия даёт `not_backup`, неизвестная — 404, неверное имя — 422.

Перед изменением схемы SQLite (`schema_version` в файле меньше `SCHEMA_VERSION`) `PlayerService` до открытия хранилища делает копию самого файла через SQLite backup API: `coach-pre-schema-<версия>-<время>.sqlite3`, хранятся две последние. Это ручное восстановление на крайний случай, приложение их не читает.

Тесты: `test_auto_backup.py` (weekly/update/off/пустая история, ротация по числу и бюджету, предпросмотр без записи и восстановление, повреждённые и неизвестные копии, снимок перед сменой схемы, общие правила проверки).
