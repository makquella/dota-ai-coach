# Читання великої історії (0.53.59)

Аудит: профілювати читання великої історії та `EXPLAIN QUERY PLAN`, не розбирати JSON розборів повторно без потреби.

**Замір.** `backend/scripts/bench_history.py` будує тимчасове сховище з N синтетичними матчами (без реальних даних) і друкує час читань, які робить лаунчер, і плани запитів. До змін, 3000 матчів: таблиця матчів, сторінка 40 — 7 мс у сховищі (23 мс через HTTP), фільтр за героєм — 1 мс, дані «Прогресу» — 7,3 мс, «Профіль» — 70 мс через HTTP. Усі списки сортувалися за `COALESCE(start_time, 0) DESC, match_id DESC`, а індекс `matches_by_time` був за `start_time`, тому SQLite щоразу будував тимчасове дерево сортування по всій історії гравця (`USE TEMP B-TREE FOR ORDER BY`).

**Зміни.**
- Індекси за виразом сортування: `matches_by_order (account_id, COALESCE(start_time, 0) DESC, match_id DESC)` і `matches_by_hero_order (account_id, hero_id, …)`. Створюються `CREATE INDEX IF NOT EXISTS` під час відкриття сховища, версія схеми не змінюється, дані не зачіпаються.
- «Профіль» читає всю історію, але лише потрібні йому колонки (`PlayerStore.profile_rows`, `PROFILE_COLUMNS`): без предметів (JSON на кожен рядок), нотаток та інших колонок таблиці.

**Після, 3000 матчів:** сторінка 40 — 0,4 мс (7 мс через HTTP), фільтр за героєм — 0,4 мс, «Прогрес» — 1,2–2,4 мс, список героїв — покривний індекс, «Профіль» — 40 мс через HTTP (решта часу — підрахунок досягнень у Python). Сортування за оцінкою/тривалістю, як і раніше, сортує (2 мс), це рідкісний вибір користувача.

**Розбір JSON.** «Прогрес» розбирає не більше 50 останніх розборів (`RECENT_MATCHES_LIMIT`), ≈1 мс на 3000 матчів; кеш розібраних розборів з інвалідацією за `updated_at` зараз не окуповується й не доданий. Якщо вікно зросте, це наступне місце.

`backend/tests/test_store_plans.py` перевіряє, що кожен порядок списків іде за індексом без тимчасового сортування і що рядки профілю збігаються за складом і порядком із таблицею матчів.
