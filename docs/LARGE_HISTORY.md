# Чтение большой истории (0.53.59)

Аудит: профилировать чтение большой истории и `EXPLAIN QUERY PLAN`, не разбирать JSON разборов повторно без нужды.

**Замер.** `backend/scripts/bench_history.py` строит временное хранилище с N синтетическими матчами (без реальных данных) и печатает время чтений, которые делает лаунчер, и планы запросов. До изменений, 3000 матчей: таблица матчей, страница 40 — 7 мс в хранилище (23 мс по HTTP), фильтр по герою — 1 мс, данные «Прогресса» — 7,3 мс, «Профиль» — 70 мс по HTTP. Все списки сортировались по `COALESCE(start_time, 0) DESC, match_id DESC`, а индекс `matches_by_time` был по `start_time`, поэтому SQLite каждый раз строил временное дерево сортировки по всей истории игрока (`USE TEMP B-TREE FOR ORDER BY`).

**Изменения.**
- Индексы по выражению сортировки: `matches_by_order (account_id, COALESCE(start_time, 0) DESC, match_id DESC)` и `matches_by_hero_order (account_id, hero_id, …)`. Создаются `CREATE INDEX IF NOT EXISTS` при открытии хранилища, версия схемы не меняется, данные не трогаются.
- «Профиль» читает всю историю, но только нужные ему колонки (`PlayerStore.profile_rows`, `PROFILE_COLUMNS`): без предметов (JSON на каждую строку), заметок и прочих колонок таблицы.

**После, 3000 матчей:** страница 40 — 0,4 мс (7 мс по HTTP), фильтр по герою — 0,4 мс, «Прогресс» — 1,2–2,4 мс, список героев — покрывающий индекс, «Профиль» — 40 мс по HTTP (оставшееся время — подсчёт достижений в Python). Сортировка по оценке/длительности по-прежнему сортирует (2 мс), это редкий выбор пользователя.

**Разбор JSON.** «Прогресс» разбирает не больше 50 последних разборов (`RECENT_MATCHES_LIMIT`), ≈1 мс на 3000 матчей; кэш разобранных разборов с инвалидацией по `updated_at` сейчас не окупается и не добавлен. Если окно вырастет, это следующее место.

`backend/tests/test_store_plans.py` проверяет, что каждый порядок списков идёт по индексу без временной сортировки, и что строки профиля совпадают по составу и порядку с таблицей матчей.
